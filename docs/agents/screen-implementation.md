# 화면 구현 순서와 원칙

## 작업 순서

1. 화면·프로토타입의 요구사항을 현재 백엔드 OpenAPI 및 생성 코드와 대조한다. 제공되는 데이터와 없는 기능을 구분하고, 서버가 보장하지 않은 특성을 가정하지 않는다.
2. 현재 API로 대체할 수 있는 더미 데이터부터 연결한다. 데이터 연결과 무관한 기능·디자인 확장은 함께 진행하지 않는다.
3. 시장 등 전역 조건은 기존 global URL 상태에서 읽는다. 요청에 영향을 주는 URL 조건은 `loaderDeps`에 포함하고, 독립적인 요청은 loader에서 병렬로 시작한다.
4. 화면은 Orval이 생성한 query options를 직접 사용한다. loader와 화면의 요청 조건을 일치시킨다. 생성된 것을 수동 `-query` 래퍼로 다시 만들지 않는다.
5. 없는 API·필드는 필요가 확인된 만큼 Overlay에 추가한다. 서버 원본은 보존하고, 제안 계약은 `x-contract-source: frontend-proposed`로 명시한다. 제안 계약의 mock 동작과 실제 백엔드 구현 여부를 구분한다.
6. 연결 중 발생한 오류를 계약·mock·화면·실서버 문제로 구분해 해결한다. 데이터 연결 후 요청받은 화면 동작을 구현한다.

## 교체 원칙

- 현재 계약과 화면 요구에 맞게 교체한다. **기존 코드를 살리거나 하위호환성을 유지하려고 옛 API, 어댑터, fallback 경로를 남기지 않는다.**
- 옛 API를 복원해 이전 화면 모델을 유지하지 않는다. 교체로 사용하지 않게 된 코드도 함께 제거한다.
- 생성 코드 직접 수정 대신 원본과 Overlay에서 생성하는 과정을 사용한다. 전체에 적용할 규칙은 스키마를 열거하지 말고 일반 규칙으로 작성한다.
- 서버 요청 실패·빈 결과를 더미 데이터로 대체하지 않는다. 미연결 데이터나 기능은 실제 제공되는 것처럼 표시하지 않는다.

## 구성과 표현

- 데이터 사용과 로딩·오류 처리가 사용하는 위치에서 선언적으로 보이게 작성한다. Suspensive는 도구이며 모든 곳에서 강제하지 않는다.
- fallback은 현재 `"로딩중"`, `"오류가 발생했습니다"` 같은 인라인 문자열을 사용한다. 반복된다는 이유로 fallback 컴포넌트나 조회 전용 래퍼를 만들지 않는다.
- 역할이 있는 도메인 컴포넌트만 분리하고, 화면 전용 코드는 해당 라우트의 `-components`에 둔다. 필요한 경우 도메인 컴포넌트 내부에서 조회한다.
- 기존 공통 UI를 조합한다. 화면의 요구를 처리하려고 공통 컴포넌트부터 확장하지 않는다.
- `const movers = data.movers`처럼 이름만 바꾸는 별칭 변수는 만들지 않는다. 변환·계산을 표현하는 변수와 구분한다.
- 숫자·등락 부호·색상은 기존 표시 컴포넌트를 활용한다. 영역 구분은 border 클래스 대신 `Separator`를 사용한다.
- 같은 식별자의 항목이 반복될 수 있는 목록은 현재 합의대로 식별자와 index를 조합해 key로 사용한다. 중복 데이터를 오류라고 가정해 임의로 제거하지 않는다.
- 요청받지 않은 캐시 시간·폴링 등 최적화 옵션, 추가 추상화, 호환 계층은 넣지 않는다.

## 실행과 검증

- 개발 서버 실행, mock 활성화, API 목적지는 독립적으로 설정한다. 조합마다 package 스크립트를 늘리지 않는다. 개발용 proxy를 배포에서도 사용하는 것으로 가정하지 않는다.
- 실제 변경의 동작을 검증한다. URL 조건에 따른 요청, 정상·빈 응답·오류 처리를 확인하고 이번 변경의 문제와 기존 오류를 구분해 보고한다.
- 확인을 위해 띄운 서버는 정리한다. 다른 작업자의 변경이나 제외된 화면은 건드리지 않는다.
